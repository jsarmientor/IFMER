Note💡 Resumen Ejecutivo de la Sesión

En esta sesión inauguramos el Tercer Corte (Datos, Inteligencia Artificial y Ética) abordando el origen de la telemetría clínica: el Internet de las Cosas Médicas (IoMT). Conoceremos la evolución del IoT desde sus inicios, la anatomía de un sistema embebido hospitalario y analizaremos a fondo el protocolo MQTT (Message Queuing Telemetry Transport), estándar de facto para la transmisión ligera y asíncrona de señales biomédicas. Finalmente, implementaremos una solución de ingeniería biomédica para el monitoreo de cadena de frío en una nevera de farmacia hospitalaria, asegurando la viabilidad térmica de vacunas y medicamentos termolábiles mediante microcontroladores (XIAO ESP32-C3 en simulador Wokwi), sensores de temperatura y humedad (DHT22), actuadores (LED de alarma), y el broker en la nube HiveMQ junto a su cliente web interactivo.

🕒 1. Evolución Histórica: Del IoT al IoMT

El Internet de las Cosas no nació de la noche a la mañana; es el resultado de décadas de convergencia entre redes de computadores, miniaturización electrónica y sensores de bajo costo.

Año Hito Tecnológico Descripción y Relevancia Impacto en Salud / Industria
1982 Máquina de Coca-Cola (Carnegie Mellon) Estudiantes de ciencias de la computación conectaron una máquina expendedora a ARPANET para saber por red si había botellas frías disponibles antes de caminar hasta ella. Primer dispositivo o electrodoméstico conectado de la historia.
1990 Internet Toaster (John Romkey) Presentada en la conferencia INTEROP, fue la primera tostadora controlada completamente a través de comandos TCP/IP mediante una interfaz SNMP. Demostración pionera de control remoto de actuadores por Internet.
1999 Kevin Ashton & MIT Auto-ID Ashton acuña formalmente la frase "Internet of Things" en Procter & Gamble al proponer tags RFID para rastrear la cadena de suministro global. En este mismo año, Andy Stanford-Clark (IBM) y Arlen Nipper crean el protocolo MQTT para telemetría satelital. Nacimiento formal del término IoT y creación del protocolo estándar de telemetría.
2008 Punto de Inflexión Poblacional Cisco Systems estima que el número de dispositivos conectados a Internet superó por primera vez al número de personas vivas en la Tierra (proporción > 1:1). Transición de un Internet de personas a un Internet de máquinas autónomas.
2016 Botnet Mirai Ataque masivo DDoS que infectó cientos de miles de cámaras y dispositivos IoT domésticos con contraseñas de fábrica para derribar servicios DNS en todo el mundo. Llamado de atención urgente sobre la ciberseguridad en dispositivos embebidos.
2020 - 2026+ IoMT, AIoT y TinyML Convergencia de biosensores portátiles (wearables), algoritmos de Inteligencia Artificial ejecutados en el microcontrolador (TinyML) y telemedicina continua. Revolución de la monitorización remota de pacientes, incubadoras y trazabilidad farmacéutica.

¿Qué diferencia al IoT tradicional del IoMT?

En una aplicación de IoT convencional (como un bombillo inteligente o un termostato doméstico), una falla temporal o una pérdida de paquetes resulta tolerable. En el IoMT (Internet of Medical Things):

  • Criticidad de vida o muerte: La pérdida del reporte de una arritmia cardíaca, la falla de un ventilador mecánico o una excursión térmica no detectada en vacunas puede costar vidas humanas o pérdidas millonarias.
  • Normativa estricta: Dispositivos y software deben ceñirse a estándares de farmacovigilancia, FDA, Invima, normativas de dispositivos médicos (ISO 13485) y privacidad de datos (Ley de Habeas Data 1581 de 2012, HIPAA, GDPR).
  • Integridad de datos: Se requiere trazabilidad inmutable y confirmación de entrega en la red.

🧠 2. Anatomía de un Dispositivo IoMT

En su nivel más elemental, cualquier dispositivo de Internet de las Cosas Médicas se compone de cuatro capas interconectadas:

  1. Sensores (Captura): Transductores que transforman magnitudes físicas (temperatura, humedad, voltaje galvánico, fotopletismografía PPG, acelerometría) en señales eléctricas calibradas.
  2. Microcontrolador / SoC (Computación en el Borde): Circuitos integrados de bajo consumo (como Seeed Studio XIAO ESP32-C3 o ESP32) que ejecutan el firmware, leen los sensores y ejecutan la lógica local de control (if / else).
  3. Conectividad (Transporte): Módulos de radiofrecuencia (Wi-Fi IEEE 802.11, Bluetooth Low Energy BLE, LoRaWAN, Cellular NB-IoT) que transportan los paquetes.
  4. Broker / Plataforma en la Nube: Servidor central encargado de recibir los mensajes de múltiples dispositivos, enrutarlos, almacenarlos y accionar alarmas en tiempo real.
  5. Actuadores & Alarmas: Dispositivos de salida (LEDs de alerta, relés para encendido de refrigeradores auxiliares, sirenas sonoras o indicadores visuales).

📡 3. El Protocolo MQTT: Fundamentos y Comparación con HTTP

¿Por qué no usar simplemente peticiones HTTP (GET / POST)?

En aplicaciones web convencionales, el protocolo estándar es HTTP/1.1 o HTTP/2, basado en un modelo Cliente-Servidor de Petición/Respuesta (Request/Response). Aunque HTTP es excelente para páginas web y APIs REST, presenta graves deficiencias en microcontroladores y dispositivos médicos alimentados por batería:

Característica HTTP (REST) MQTT (Message Queuing Telemetry Transport)
Paradigma Petición / Respuesta (Request / Response, Síncrono) Publicación / Suscripción (Publish / Subscribe, Asíncrono)
Cabecera del paquete Pesada (mínimo centenas de bytes a varios KB con headers HTTP) Ultraligera (cabecera fija mínima de tan solo 2 bytes)
Consumo de Batería y CPU Alto (crea y destruye sockets TCP en cada reporte) Extremadamente bajo (conexión TCP persistente con Keep-Alive)
Modelo de Datos Sondeo constante (Polling) para enterarse de novedades Empuje en tiempo real (Push) inmediato hacia los suscriptores
Conocimiento mutuo El cliente debe conocer la dirección IP / URL exacta del servidor Desacoplamiento total: Clientes solo conocen al Broker

El Desacoplamiento Tridimensional de MQTT

Una de las mayores virtudes pedagógicas y operativas de MQTT es que rompe la dependencia directa entre los dispositivos:

  1. Desacoplamiento Espacial: El sensor que mide la temperatura no tiene idea de qué computadores, teléfonos o navegadores están leyendo su dato. Solo publica en un canal (tópico) en el Broker.
  2. Desacoplamiento Temporal: El publicador y el suscriptor no tienen que estar conectados a la red al mismo tiempo. Mediante banderas como Retained Messages o sesiones persistentes, un suscriptor que se conecte después puede recibir de inmediato el último estado conocido.
  3. Desacoplamiento de Sincronización: La operación de publicación es asíncrona y no bloqueante. El microcontrolador envía su lectura y continúa de inmediato ejecutando su ciclo de control sin esperar a que otros la procesen.

Niveles de Calidad de Servicio (QoS - Quality of Service)

MQTT ofrece tres niveles nativos de garantía en la entrega de paquetes según la criticidad del dato:

  • QoS 0 — “At most once” (A lo sumo una vez / Fuego y olvido):
    El mensaje se envía sin confirmación a nivel de aplicación. Se apoya únicamente en la confiabilidad de la capa TCP subyacente. Si se corta el enlace, el paquete se pierde. Es ideal para telemetría no crítica de alta frecuencia.
  • QoS 1 — “At least once” (Al menos una vez):
    El emisor retransmite el mensaje hasta recibir un paquete de reconocimiento (PUBACK) del Broker. Se garantiza que el mensaje llega, pero si hay fluctuaciones de red pueden presentarse mensajes duplicados.
  • QoS 2 — “Exactly once” (Exactamente una vez):
    Es el nivel más confiable y estricto. Se realiza un protocolo de apretón de manos (handshake) en 4 pasos (PUBLISH \(\rightarrow\) PUBREC \(\rightarrow\) PUBREL \(\rightarrow\) PUBCOMP). Garantiza que el mensaje llega exactamente una sola vez, sin pérdidas ni duplicados. Es el nivel idóneo para eventos médicos críticos, tales como dosificación de medicamentos por bombas de infusión o alarmas de parada cardiorrespiratoria.

🗂️ 4. Sintaxis y Jerarquía de Tópicos MQTT

Los tópicos (topics) en MQTT son cadenas de texto organizadas en forma de árbol jerárquico separadas por diagonales (/). Son sensibles a mayúsculas y minúsculas (case-sensitive).

Reglas de diseño de tópicos:

  • No utilizar espacios ni caracteres especiales con tildes.
  • Diseñar de lo más general a lo más específico (ej. institución/servicio/equipo/variable).
  • Wildcards (Comodines) para Suscripción:
    • + (Comodín de un solo nivel): Reemplaza exactamente un nivel del árbol.
      • Ejemplo: hospital/farmacia/+/temperatura permite recibir la temperatura de todas las neveras de la farmacia (nevera_01, nevera_02, etc.).
    • # (Comodín multinivel): Debe ubicarse siempre al final del tópico y captura todos los subniveles inferiores.
      • Ejemplo: hospital/farmacia/# suscribe a todos los mensajes (temperatura, humedad, estados de puerta, alarmas y actuadores).

🏥 5. Caso Clínico de Estudio: Cadena de Frío en Farmacia Hospitalaria

Justificación Biomédica y Farmacéutica

En los servicios de salud (farmacia central, oncología, vacunación, banco de sangre), la conservación de medicamentos biológicos, vacunas (antirrábica, influenza, COVID-19, hepatitis B) e insulinas exige una temperatura constante en el rango estricto de:

\[\mathbf{2.0^\circ\text{C} \le \text{Temperatura} \le 8.0^\circ\text{C}}\]

La humedad relativa debe controlarse típicamente entre el 30% y el 60% para impedir la condensación y el deterioro de los empaques primarios.

  • Excursión térmica por calor (\(> 8.0^\circ\text{C}\)): Ocasiona desnaturalización irreversible de proteínas en vacunas y pérdida total de efectividad terapéutica.
  • Excursión térmica por congelamiento (\(< 2.0^\circ\text{C}\)): Las vacunas con adyuvantes a base de sales de aluminio se desestabilizan y pierden su inmunogenicidad.

// DECLARACIÓN DE CALLBACK PARA MENSAJES ENTRANTES (ÓRDENES REMOTAS)

void callback(char* topic, byte* message, unsigned int length) {
  Serial.print("Llegó un mensaje del tópico: ");
  Serial.print(topic);
  Serial.print(". Mensaje: ");

  String messageTemp = "";
  for (int i = 0; i < length; i++) {
    Serial.print((char)message[i]);
    messageTemp += (char)message[i];
  }
  Serial.println();

  // Control remoto del actuador LED
  if (String(topic) == "hospital/farmacia/nevera_01/led" || String(topic) == "Led") {
    if (messageTemp == "on" || messageTemp == "ON") {
      digitalWrite(lamp, HIGH);
      Serial.println(">>> ACTUADOR: LED encendido por orden remota");
    }
    else if (messageTemp == "off" || messageTemp == "OFF") {
      digitalWrite(lamp, LOW);
      Serial.println(">>> ACTUADOR: LED apagado por orden remota");
    }
  }
}

// RECONEXIÓN AL BROKER MQTT

void reconnect() {
  while (!client.connected()) {
    Serial.print("Intentando conectar al broker HiveMQ...");

    if (client.connect(clientName.c_str())) {
      Serial.println(" ¡Conectado exitosamente!");

      // Suscripción a los tópicos de control remoto para el actuador LED
      client.subscribe("hospital/farmacia/nevera_01/led");
      client.subscribe("Led");
      Serial.println("Suscrito a los tópicos de control: Led y hospital/farmacia/nevera_01/led");

    } else {
      Serial.print(" Fallo de conexión, rc=");
      Serial.print(client.state());
      Serial.println(" Intentando nuevamente en 3 segundos...");
      delay(3000);
    }
  }
}

  }

  Serial.println("");
  Serial.print("Conexión WiFi establecida. Dirección IP asignada: ");
  Serial.println(WiFi.localIP());
}

// CONFIGURACIÓN INICIAL (SETUP)
// ==============================================================================
void setup() {
  Serial.begin(9600);

  // Generar ID único usando la MAC
  generarNombreCliente();

  // Conectar a Wi-Fi
  setup_wifi();

  // Configurar servidor MQTT y función de escucha
  client.setServer(mqtt_server, 1883);
  client.setCallback(callback);

  // Inicializar periféricos
  pinMode(lamp, OUTPUT);
  dht.begin();

  lastSend = 0;
  delay(2000);
}

// ==============================================================================
// LECTURA DEL SENSOR DHT22
// ==============================================================================
void GetSensor() {
  h = dht.readHumidity();
  t = dht.readTemperature();

  if (isnan(h) || isnan(t)) {
    Serial.println("[ERROR] Falla al leer el sensor DHT22!");
    return;
  }
}

// ==============================================================================
// ARMADO DEL MENSAJE EN FORMATO JSON
// ==============================================================================
void CrearJson() {
  String temperatura = String(t, 2);
  String humedad = String(h, 2);

  // Construcción del paquete JSON
  payload = "{";
  payload += "\"temp\":";
  payload += temperatura;
  payload += ",";
  payload += "\"hum\":";
  payload += humedad;

  // Lógica médica para cadena de frío en farmacia: rango 2.0 °C a 8.0 °C
  if (t > 8.0 || t < 2.0) {
    payload += ",\"alerta\":true";
    payload += ",\"estado\":\"EXCURSION_TERMICA\"";
  } else {
    payload += ",\"alerta\":false";
    payload += ",\"estado\":\"NORMAL\"";
  }

  payload += "}";
}

// ==============================================================================
// PUBLICACIÓN DE LA TELEMETRÍA
// ==============================================================================
void PublicarMensaje() {
  char attributes[150];
  payload.toCharArray(attributes, 150);

  // Publicación en el tópico hospitalario y en el tópico general
  client.publish("hospital/farmacia/nevera_01/telemetria", attributes);
  client.publish("TopicURSensorTempHum", attributes);

  Serial.print("[MQTT Enviado] -> ");
  Serial.println(attributes);
}

// ==============================================================================
// CICLO PRINCIPAL (LOOP)
// ==============================================================================
void loop() {
  if (!client.connected()) {
    reconnect();
  }

  // Medir y publicar cada 2 segundos
  if (millis() - lastSend > 2000) {
    GetSensor();
    CrearJson();
    PublicarMensaje();
    lastSend = millis();
  }

  client.loop(); // Mantiene activa la conexión MQTT y procesa callbacks
}

### ¿Qué diferencia al IoT tradicional del IoMT?

En una aplicación de IoT convencional (como un bombillo inteligente o un termostato doméstico), una falla temporal o una pérdida de paquetes resulta tolerable. En el **IoMT (Internet of Medical Things)**:

* **Criticidad de vida o muerte:** La pérdida del reporte de una arritmia cardíaca, la falla de un ventilador mecánico o una excursión térmica no detectada en vacunas puede costar vidas humanas o pérdidas millonarias.
* **Normativa estricta:** Dispositivos y software deben ceñirse a estándares de farmacovigilancia, FDA, Invima, normativas de dispositivos médicos (ISO 13485) y privacidad de datos (Ley de Habeas Data 1581 de 2012, HIPAA, GDPR).
* **Integridad de datos:** Se requiere trazabilidad inmutable y confirmación de entrega en la red.

## 🧠 2. Anatomía de un Dispositivo IoMT

En su nivel más elemental, cualquier dispositivo de Internet de las Cosas Médicas se compone de cuatro capas interconectadas:

```{mermaid}
flowchart LR
    A["🌡️ Sensores Fisiológicos / Físicos"] --> B["📟 Microcontrolador / SoC (Lógica & Procesamiento)"]
    B --> C["📡 Enlace de Red (Wi-Fi, BLE, LoRa, Ethernet)"]
    C --> D["☁️ Broker / Servidor Nube (MQTT / IoT Hub)"]
    D --> E["🚨 Actuadores / Alarmas Clínicas"]
    D --> F["📊 Dashboards & Historial Clínico"]

1. **Sensores (Captura):** Transductores que transforman magnitudes físicas (temperatura, humedad, voltaje galvánico, fotopletismografía PPG, acelerometría) en señales eléctricas calibradas.
2. **Microcontrolador / SoC (Computación en el Borde):** Circuitos integrados de bajo consumo (como Seeed Studio XIAO ESP32-C3 o ESP32) que ejecutan el firmware, leen los sensores y ejecutan la lógica local de control (`if / else`).
3. **Conectividad (Transporte):** Módulos de radiofrecuencia (Wi-Fi IEEE 802.11, Bluetooth Low Energy BLE, LoRaWAN, Cellular NB-IoT) que transportan los paquetes.
4. **Broker / Plataforma en la Nube:** Servidor central encargado de recibir los mensajes de múltiples dispositivos, enrutarlos, almacenarlos y accionar alarmas en tiempo real.
5. **Actuadores & Alarmas:** Dispositivos de salida (LEDs de alerta, relés para encendido de refrigeradores auxiliares, sirenas sonoras o indicadores visuales).

## 📡 3. El Protocolo MQTT: Fundamentos y Comparación con HTTP

### ¿Por qué no usar simplemente peticiones HTTP (GET / POST)?

En aplicaciones web convencionales, el protocolo estándar es **HTTP/1.1** o **HTTP/2**, basado en un modelo **Cliente-Servidor de Petición/Respuesta (Request/Response)**. Aunque HTTP es excelente para páginas web y APIs REST, presenta graves deficiencias en microcontroladores y dispositivos médicos alimentados por batería:

    </tr>
  </tbody>
</table>
</div>
```

### El Desacoplamiento Tridimensional de MQTT

Una de las mayores virtudes pedagógicas y operativas de MQTT es que rompe la dependencia directa entre los dispositivos:

1. **Desacoplamiento Espacial:** El sensor que mide la temperatura no tiene idea de qué computadores, teléfonos o navegadores están leyendo su dato. Solo publica en un canal (*tópico*) en el Broker.
2. **Desacoplamiento Temporal:** El publicador y el suscriptor no tienen que estar conectados a la red al mismo tiempo. Mediante banderas como *Retained Messages* o sesiones persistentes, un suscriptor que se conecte después puede recibir de inmediato el último estado conocido.
3. **Desacoplamiento de Sincronización:** La operación de publicación es asíncrona y no bloqueante. El microcontrolador envía su lectura y continúa de inmediato ejecutando su ciclo de control sin esperar a que otros la procesen.

### Niveles de Calidad de Servicio (QoS - Quality of Service)

MQTT ofrece tres niveles nativos de garantía en la entrega de paquetes según la criticidad del dato:

* **QoS 0 — "At most once" (A lo sumo una vez / Fuego y olvido):**  
  El mensaje se envía sin confirmación a nivel de aplicación. Se apoya únicamente en la confiabilidad de la capa TCP subyacente. Si se corta el enlace, el paquete se pierde. Es ideal para telemetría no crítica de alta frecuencia.
* **QoS 1 — "At least once" (Al menos una vez):**  
  El emisor retransmite el mensaje hasta recibir un paquete de reconocimiento (`PUBACK`) del Broker. Se garantiza que el mensaje llega, pero si hay fluctuaciones de red pueden presentarse mensajes duplicados.
* **QoS 2 — "Exactly once" (Exactamente una vez):**  
  Es el nivel más confiable y estricto. Se realiza un protocolo de apretón de manos (*handshake*) en 4 pasos (`PUBLISH` $\rightarrow$ `PUBREC` $\rightarrow$ `PUBREL` $\rightarrow$ `PUBCOMP`). Garantiza que el mensaje llega exactamente una sola vez, sin pérdidas ni duplicados. Es el nivel idóneo para eventos médicos críticos, tales como **dosificación de medicamentos por bombas de infusión** o **alarmas de parada cardiorrespiratoria**.

## 🗂️ 4. Sintaxis y Jerarquía de Tópicos MQTT

Los tópicos (*topics*) en MQTT son cadenas de texto organizadas en forma de árbol jerárquico separadas por diagonales (`/`). Son **sensibles a mayúsculas y minúsculas** (*case-sensitive*).

### Reglas de diseño de tópicos:
* No utilizar espacios ni caracteres especiales con tildes.
* Diseñar de lo más general a lo más específico (ej. `institución/servicio/equipo/variable`).
* **Wildcards (Comodines) para Suscripción:**
  * `+` (Comodín de un solo nivel): Reemplaza exactamente un nivel del árbol.
    * Ejemplo: `hospital/farmacia/+/temperatura` permite recibir la temperatura de todas las neveras de la farmacia (`nevera_01`, `nevera_02`, etc.).
  * `#` (Comodín multinivel): Debe ubicarse siempre al final del tópico y captura todos los subniveles inferiores.
    * Ejemplo: `hospital/farmacia/#` suscribe a todos los mensajes (temperatura, humedad, estados de puerta, alarmas y actuadores).

## 🏥 5. Caso Clínico de Estudio: Cadena de Frío en Farmacia Hospitalaria

### Justificación Biomédica y Farmacéutica
En los servicios de salud (farmacia central, oncología, vacunación, banco de sangre), la conservación de medicamentos biológicos, vacunas (antirrábica, influenza, COVID-19, hepatitis B) e insulinas exige una temperatura constante en el rango estricto de:

$$\mathbf{2.0^\circ\text{C} \le \text{Temperatura} \le 8.0^\circ\text{C}}$$

La humedad relativa debe controlarse típicamente entre el **30% y el 60%** para impedir la condensación y el deterioro de los empaques primarios. 

* **Excursión térmica por calor ($> 8.0^\circ\text{C}$):** Ocasiona desnaturalización irreversible de proteínas en vacunas y pérdida total de efectividad terapéutica.
* **Excursión térmica por congelamiento ($< 2.0^\circ\text{C}$):** Las vacunas con adyuvantes a base de sales de aluminio se desestabilizan y pierden su inmunogenicidad.

### 💻 Código Fuente en C++ (`sketch.ino`)

Copie y pegue el siguiente código en la pestaña `sketch.ino` de Wokwi. Este código incluye:
* Generación automática del ID único de cliente MQTT utilizando la dirección MAC física del ESP32.
* Conexión a la red Wi-Fi virtual `Wokwi-GUEST`.
* Conexión con el broker gratuito **HiveMQ** (`broker.hivemq.com` en puerto `1883`).
* Publicación periódica del JSON con temperatura, humedad y estado clínico de la cadena de frío.
* Función de escucha (*callback*) para encender o apagar el actuador LED desde el cliente web mediante el tópico `Led` o `hospital/farmacia/nevera_01/led`.

```cpp
// ==============================================================================
// SISTEMA IoMT DE TELEMETRÍA Y CONTROL DE CADENA DE FRÍO - FARMACIA HOSPITALARIA
// Asignatura: Informática Médica (IFMER 2026-II) - Universidad del Rosario
// Docente: Prof. Jefferson Sarmiento Rojas
// Placa: Seeed Studio XIAO ESP32-C3 | Sensor: DHT22 en D2 | LED en D4
// Broker: HiveMQ (broker.hivemq.com:1883)
// ==============================================================================

// 1. Importar librerías
#include "WiFi.h"          // Conexión WiFi
#include "PubSubClient.h"  // Cliente MQTT
#include "DHT.h"           // Sensor DHT22

// Pin de salida que gobierna el LED actuador
const int lamp = D4;

// 2. Configuración de red inalámbrica
const char* ssid = "Wokwi-GUEST";           // Red virtual de Wokwi
const char* password = "";                  // Sin contraseña en simulador
const char* mqtt_server = "broker.hivemq.com"; // Broker MQTT público y gratuito HiveMQ

// 3. Cliente WiFi y cliente MQTT
WiFiClient espClient;
PubSubClient client(espClient);
unsigned long lastSend;
int status = WL_IDLE_STATUS;

// Nombre de cliente MQTT generado automáticamente
String clientName;

// 4. Configuración del sensor
#define DHTPIN D2      // Pin de datos del DHT22 conectado a D2
#define DHTTYPE DHT22  // Referencia del sensor DHT22

DHT dht(DHTPIN, DHTTYPE);

float h, t;            // Variables de humedad y temperatura

// 5. Mensaje que se publica en formato JSON
String payload;

// ==============================================================================
// GENERAR NOMBRE DE CLIENTE MQTT A PARTIR DE LA MAC DEL ESP32
// ==============================================================================
void generarNombreCliente() {
  uint64_t mac = ESP.getEfuseMac();
  char nombre[30];

  snprintf(
    nombre,
    sizeof(nombre),
    "ESP32_%012llX",
    mac
  );

  clientName = String(nombre);

  Serial.print("Nombre cliente MQTT generado: ");
  Serial.println(clientName);
}

// ==============================================================================
// DECLARACIÓN DE CALLBACK PARA MENSAJES ENTRANTES (ÓRDENES REMOTAS)
// ==============================================================================
void callback(char* topic, byte* message, unsigned int length) {
  Serial.print("Llegó un mensaje del tópico: ");
  Serial.print(topic);
  Serial.print(". Mensaje: ");

  String messageTemp = "";
  for (int i = 0; i < length; i++) {
    Serial.print((char)message[i]);
    messageTemp += (char)message[i];
  }
  Serial.println();

  // Control remoto del actuador LED
  if (String(topic) == "hospital/farmacia/nevera_01/led" || String(topic) == "Led") {
    if (messageTemp == "on" || messageTemp == "ON") {
      digitalWrite(lamp, HIGH);
      Serial.println(">>> ACTUADOR: LED encendido por orden remota");
    }
    else if (messageTemp == "off" || messageTemp == "OFF") {
      digitalWrite(lamp, LOW);
      Serial.println(">>> ACTUADOR: LED apagado por orden remota");
    }
  }
}

// ==============================================================================
// RECONEXIÓN AL BROKER MQTT
// ==============================================================================
void reconnect() {
  while (!client.connected()) {
    Serial.print("Intentando conectar al broker HiveMQ...");

    if (client.connect(clientName.c_str())) {
      Serial.println(" ¡Conectado exitosamente!");

      // Suscripción a los tópicos de control remoto para el actuador LED
      client.subscribe("hospital/farmacia/nevera_01/led");
      client.subscribe("Led");
      Serial.println("Suscrito a los tópicos de control: Led y hospital/farmacia/nevera_01/led");

    } else {
      Serial.print(" Fallo de conexión, rc=");
      Serial.print(client.state());
      Serial.println(" Intentando nuevamente en 3 segundos...");
      delay(3000);
    }
  }
}

// ==============================================================================
// CONEXIÓN A LA RED INALÁMBRICA WI-FI
// ==============================================================================
void setup_wifi() {
  delay(10);
  Serial.println();
  Serial.print("Conectando a la red: ");
  Serial.println(ssid);

  WiFi.begin(ssid, password);

  while (WiFi.status() != WL_CONNECTED) {
    delay(200);
    Serial.print(".");
  }

  Serial.println("");
  Serial.print("Conexión WiFi establecida. Dirección IP asignada: ");
  Serial.println(WiFi.localIP());
}

// ==============================================================================
// CONFIGURACIÓN INICIAL (SETUP)
// ==============================================================================
void setup() {
  Serial.begin(9600);

  // Generar ID único usando la MAC
  generarNombreCliente();

  // Conectar a Wi-Fi
  setup_wifi();

  // Configurar servidor MQTT y función de escucha
  client.setServer(mqtt_server, 1883);
  client.setCallback(callback);

  // Inicializar periféricos
  pinMode(lamp, OUTPUT);
  dht.begin();

  lastSend = 0;
  delay(2000);
}

// ==============================================================================
// LECTURA DEL SENSOR DHT22
// ==============================================================================
void GetSensor() {
  h = dht.readHumidity();
  t = dht.readTemperature();

  if (isnan(h) || isnan(t)) {
    Serial.println("[ERROR] Falla al leer el sensor DHT22!");
    return;
  }
}

// ==============================================================================
// ARMADO DEL MENSAJE EN FORMATO JSON
// ==============================================================================
void CrearJson() {
  String temperatura = String(t, 2);
  String humedad = String(h, 2);

  // Construcción del paquete JSON
  payload = "{";
  payload += "\"temp\":";
  payload += temperatura;
  payload += ",";
  payload += "\"hum\":";
  payload += humedad;

  // Lógica médica para cadena de frío en farmacia: rango 2.0 °C a 8.0 °C
  if (t > 8.0 || t < 2.0) {
    payload += ",\"alerta\":true";
    payload += ",\"estado\":\"EXCURSION_TERMICA\"";
  } else {
    payload += ",\"alerta\":false";
    payload += ",\"estado\":\"NORMAL\"";
  }

  payload += "}";
}

// ==============================================================================
// PUBLICACIÓN DE LA TELEMETRÍA
// ==============================================================================
void PublicarMensaje() {
  char attributes[150];
  payload.toCharArray(attributes, 150);

  // Publicación en el tópico hospitalario y en el tópico general
  client.publish("hospital/farmacia/nevera_01/telemetria", attributes);
  client.publish("TopicURSensorTempHum", attributes);

  Serial.print("[MQTT Enviado] -> ");
  Serial.println(attributes);
}

// ==============================================================================
// CICLO PRINCIPAL (LOOP)
// ==============================================================================
void loop() {
  if (!client.connected()) {
    reconnect();
  }

  // Medir y publicar cada 2 segundos
  if (millis() - lastSend > 2000) {
    GetSensor();
    CrearJson();
    PublicarMensaje();
    lastSend = millis();
  }

  client.loop(); // Mantiene activa la conexión MQTT y procesa callbacks
}
```
