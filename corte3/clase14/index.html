Clase 14: Guía del Proyecto Final Integrador

Semana 14 | Corte 3 — De la Normativa (Res. 866/2021) a la Aplicación Web (PHP CRUD o HL7 FHIR + SMART on FHIR) y Autoevaluación con Agentes IA

Author

Prof. Jefferson Sarmiento Rojas, Ph.D (c)

Published

November 17, 2026

💻 Ver Presentación de Diapositivas

🎯 Objetivos de la Clase

    1. Ruta A: Aplicación Web CRUD con HTML + Bootstrap + PHP + MySQL (basada en el diseño inicial de la tabla pacientes a partir del diccionario de datos y consultas preparadas).
    2. Ruta B: Aplicación Web Interoperable HL7 FHIR R4 + SMART on FHIR (interfaz web en HTML + JS con consumo RESTful de recursos Patient, Condition / Observation alineados al RDA/IHCE y contexto de lanzamiento OAuth2/SMART).

🌉 1. Del Reto de la Clase 06 al Proyecto Final Integrador

💡 De dónde venimos y hacia dónde vamos

En la Clase 06 aprendimos el método de ingeniería de datos clínicos sobre un archivo real (BD.xlsx, 67 equipos biomédicos × 31 columnas): Auditar la fuente → Seleccionar y tipificar las variables → Construir el Diccionario de Datos → Crear la tabla inicial en MySQL → Implementar un CRUD funcional.

En aquel Paso 13 dejamos planteado el gran reto: aplicar exactamente el mismo rigor metodológico al registro e identificación de pacientes, donde la fuente de verdad ya no es un Excel del hospital, sino la ley colombiana. Hoy en la Clase 14 consolidamos la guía del Proyecto Final Integrador con las dos opciones tecnológicas (PHP CRUD o HL7 FHIR + SMART on FHIR) y el sistema de evaluación automatizada por agentes.

1.1 El Requerimiento Normativo: Resolución 866 de 2021 (IHCE / RDA)

El sistema que cada grupo entregará debe gestionar la Identificación y Atención Básica del Paciente cumpliendo el Anexo Técnico de la Resolución 866 de 2021 del Ministerio de Salud y Protección Social (Conjunto de datos relevantes para la Interoperabilidad de la Historia Clínica Electrónica - IHCE).

  1. Consulta Normativa: Revisar el Anexo Técnico de la Resolución 866 de 2021 (Variables de Identificación del Usuario/Paciente y Datos de Contacto/Atención). 📄 Descargar Resolución 866 de 2021 — MinSalud (PDF)
  2. Diccionario de Datos Normativo: Seleccionar y tipificar las variables según la norma (por ejemplo: por qué el Número de Documento jamás puede ser INT —perdería ceros a la izquierda en registros civiles o pasaportes alfanuméricos—, y por qué el Municipio usa el código oficial DIVIPOLA – DANE).
  3. Implementación Tecnológica (Elija UNA de las dos rutas):
Característica 🛠️ Ruta A: Aplicación Web CRUD (PHP + MySQL) 🌐 Ruta B: Aplicación Web HL7 FHIR R4 + SMART on FHIR
Enfoque Arquitectónico e Interfaz Web (Obligatoria) Interfaz Web funcional (index.php + modificar.php con HTML5/Bootstrap) servida desde XAMPP (Apache + PHP 8 + MySQL). Interfaz Web funcional (launch.html + index.html + app.js con HTML5/Bootstrap + fetch / fhirclient) conectada a un servidor FHIR R4 (HAPI FHIR / SMART Sandbox). (⚠️ No basta usar Postman: debe existir una interfaz gráfica web operativa).
Modelo de Datos (Diseño Inicial) Diseño inicial de la tabla pacientes en MySQL (CREATE TABLE pacientes) con llave primaria (IdPaciente), tipos de datos atómicos (VARCHAR, DATE, CHAR) y correspondencia exacta con su Diccionario de Datos. Recurso Patient (perfil RDA Colombia con identificadores RNEC y código DIVIPOLA) vinculado al menos a un recurso clínico (Observation o Condition CIE-10/SNOMED).
Operaciones desde la Interfaz Web (CRUD) Formulario web CREATE (INSERT), tabla web con buscador READ (SELECT), formulario pre-diligenciado UPDATE, botón de baja lógica (EstadoPaciente = 0) o eliminación controlada. Formulario web CREATE (POST /Patient), tabla web con buscador READ (GET /Patient?identifier=...), edición en el formulario UPDATE (PUT /Patient/{id}), botón de inactivación lógica ("active": false).
Calidad de Código y Buenas Prácticas Consultas preparadas (prepare() + bind_param()), htmlspecialchars(), control de excepciones (try/catch para duplicados #1062). Lanzamiento SMART on FHIR (launch.html + index.html), manejo de scopes (launch, patient/*.read, patient/*.write), renderizado seguro (textContent) y trazabilidad meta.versionId.

2.1 Arquitectura de Archivos y Código Base de la Interfaz Web (Ruta A vs. Ruta B)












Important⚠️ Regla de Oro: ¡Ambas rutas requieren una Interfaz Web Funcional!







Si su grupo elige la Ruta B (HL7 FHIR + SMART on FHIR), NO basta con mostrar peticiones sueltas en Postman. Al igual que los grupos de PHP, deben construir una aplicación web con interfaz gráfica (HTML + Bootstrap + JavaScript) desde la cual el usuario médico pueda registrar pacientes (POST), buscarlos y listarlos en una tabla (GET), editarlos (PUT) e inactivarlos (active: false).

// 2. js/app.js — Lógica CRUD desde la Interfaz Web contra el Servidor FHIR R4
const FHIR_BASE = "https://hapi.fhir.org/baseR4"; // O cliente SMART: FHIR.oauth2.ready()

// CREATE (POST /Patient desde el formulario web)
async function guardarPacienteWeb(evento) {
  evento.preventDefault();
  const recursoPatient = {
    resourceType: "Patient",
    active: true,
    identifier: [{
      use: "official",
      type: { coding: [{ system: "http://terminology.hl7.org/CodeSystem/v2-0203", code: document.getElementById("tipoDoc").value }] },
      system: "https://fhir.minsalud.gov.co/rda/NamingSystem/RNEC",
      value: document.getElementById("numDoc").value.trim()
    }],
    name: [{
      use: "official",
      family: document.getElementById("apellidos").value.trim(),
      given: document.getElementById("nombres").value.trim().split(/\s+/)
    }],
    gender: document.getElementById("genero").value,
    birthDate: document.getElementById("fechaNac").value,
    address: [{
      city: document.getElementById("municipioNombre").value,
      extension: [{
        url: "https://fhir.minsalud.gov.co/rda/StructureDefinition/DivipolaMunicipio",
        valueCoding: { system: "https://www.dane.gov.co/divipola", code: document.getElementById("codigoDivipola").value }
      }]
    }]
  };

  const resp = await fetch(`${FHIR_BASE}/Patient`, {
    method: "POST",
    headers: { "Content-Type": "application/fhir+json", "Accept": "application/fhir+json" },
    body: JSON.stringify(recursoPatient)
  });
  const creado = await resp.json();
  await listarPacientesEnTablaWeb(); // Refresca la tabla HTML
}

// READ (GET /Patient y renderizado seguro con textContent en la tabla HTML)
async function listarPacientesEnTablaWeb(filtro = "") {
  const url = filtro
    ? `${FHIR_BASE}/Patient?identifier=${encodeURIComponent(filtro)}&_count=15`
    : `${FHIR_BASE}/Patient?_sort=-_lastUpdated&_count=15`;
  const resp = await fetch(url, { headers: { "Accept": "application/fhir+json" } });
  const bundle = await resp.json();
  const tbody = document.getElementById("tablaPacientesFhir");
  tbody.innerHTML = "";

  (bundle.entry || []).forEach(item => {
    const p = item.resource;
    const tr = document.createElement("tr");
    const tdDoc = document.createElement("td");
    tdDoc.textContent = p.identifier?.[0]?.value || "Sin doc"; // Anti-XSS con textContent
    const tdNombre = document.createElement("td");
    tdNombre.textContent = `${p.name?.[0]?.family || ""}, ${(p.name?.[0]?.given || []).join(" ")}`;
    tr.append(tdDoc, tdNombre);
    tbody.appendChild(tr);
  });
}

// BAJA LÓGICA (PUT /Patient/{id} cambiando active: false sin destruir el historial)
async function inactivarPacienteWeb(idPaciente) {
  const resGet = await fetch(`${FHIR_BASE}/Patient/${idPaciente}`);
  const paciente = await resGet.json();
  paciente.active = false; // Baja lógica normativa
  await fetch(`${FHIR_BASE}/Patient/${idPaciente}`, {
    method: "PUT",
    headers: { "Content-Type": "application/fhir+json" },
    body: JSON.stringify(paciente)
  });
  await listarPacientesEnTablaWeb();
}
















🤖 3. ¿Cómo Funciona la Evaluación con Agentes de IA y Cómo Preparar sus Insumos?


Para evaluar su Proyecto Final Integrador de manera objetiva, transparente y reproducible, este módulo incorpora un Sistema Multi-Agente de Autocalificación. Antes de la sustentación oficial de la Clase 15, cada grupo debe validar su proyecto utilizando esta herramienta.




3.1 ¿Qué insumos debe preparar y subir el grupo al Evaluador?


El sistema requiere un Paquete Híbrido de Entrega compuesto por Código Fuente + Video de Demostración y Transcripción del Discurso Oral. A continuación se explica por qué ambos insumos son indispensables para los agentes evaluadores:












Insumo de Entrega
¿Qué auditan los Agentes de IA en este insumo?
¿Qué ocurre si el grupo no lo incluye?
Requisito para la Entrega






1. Archivos de Código Fuente (.sql, .php, .html, .js, .json)
Los Agentes 1, 2 y 3 inspeccionan el diseño inicial de la tabla pacientes (o recurso Patient en FHIR), los tipos de datos según la Resolución 866 de 2021, la interfaz web (<form> y <table>), las 4 operaciones del flujo CRUD/REST (INSERT/POST, SELECT/GET, UPDATE/PUT, baja lógica) y el uso de consultas preparadas (prepare()).
Los Criterios 1 a 5 reciben automáticamente 0.0 / 5.0.
✅ Obligatorio (subir archivos o pegar el código integrado en el panel 1️⃣).




2. Video de Sustentación (.mp4 / .webm, 3 a 5 min)
El Agente 4 verifica la evidencia del archivo de video (duración reglamentaria de 3 a 6 minutos, peso y formato) donde el grupo muestra la interfaz web funcionando en vivo con todas sus operaciones.
El Criterio 7 (Demostración Funcional en Video) recibe automáticamente 0.0 / 5.0 (y 1.0 / 5.0 si dura menos de 1 minuto).
✅ Obligatorio (subir el archivo .mp4/.webm en el panel 2️⃣).




3. Transcripción del Discurso Oral del Grupo
El Agente 4 analiza la argumentación técnica y normativa del equipo (extensión mínima de 110 palabras y rigor terminológico sobre la Resolución 866 de 2021, tipos de datos VARCHAR/DATE, CRUD y validaciones).
El Criterio 6 (Claridad del Discurso Oral) recibe automáticamente 0.0 / 5.0 si está vacío o 1.0 / 5.0 si es superficial.
✅ Obligatorio (pegar la transcripción o guion detallado de la intervención oral en el panel 2️⃣).
